01关卡一定可解

按行进距离而非时间触发生成，速度变化时障碍间距依然稳定；每行最多占用 laneCount - 1 条轨道，永远留一条空轨道，并把晶体放在这条安全路径上作为引导。难度只改速度、间距和双障碍概率，不突破这条约束。

追问「怎么保证不会生成死局」→ 讲洗牌后取前 count 条、freeLane 从剩余轨道里选；count 被 Min 限制在 laneCount-1。

02扫掠碰撞：高速不漏判

不用 Collider / Rigidbody。每帧记录移动前的 z，只在 prevZ < 0 且 z ≥ 0 时结算一次 —— 判定的是「跨过玩家平面」这个事件，与单帧位移大小无关。结算用实际 x 坐标 + 随姿态变化的 AABB 高度区间，避免切轨插值途中按轨道编号误判。

追问「为什么不用物理」→ 规则明确的跑酷只需三个条件，省掉固定步长、碰撞矩阵与回调开销，也更好写测试；代价是没有真实物理反馈。

05高频追问 · 回答骨架点开看要点
为什么选 Unity 而不是 Unreal / Godot？

C# 迭代快、组件模型适合小原型，移动端与跨平台导出链成熟，URP 易降配。Unreal 的 Nanite/Lumen 对低多边形风格过剩；若岗位偏写实 3A，会选 UE5 —— 选型取决于目标平台和团队。

不同帧率手感怎么保证一致？

位移按 dt 积分并 clamp 到 0.05s 防止切后台瞬移；横向用 1 − exp(−k·dt) 而非线性 lerp，对任意 dt 收敛到同一时间常数；跃升用显式欧拉 vy −= g·dt、y += vy·dt。

踩过什么坑？

① 初版按时间生成，速度上来后障碍挤在一起 → 改为按行进距离；② 按轨道编号判碰撞，切轨插值途中误判 → 改用实际 x 坐标；③ 模板场景自带相机和光，运行时再建会过曝 → 复用 Camera.main 并禁用多余光源；④ 烘焙时运行时 new Material 不序列化 → 加 PersistMaterials() 落盘为 .mat。

性能瓶颈在哪、怎么优化？

主要是 DrawCall（护栏/障碍独立 Mesh）与粒子创建。用 Profiler 看 GC Alloc、Frame Debugger 看合批；顺序是材质共享 → GPU Instancing / SRP Batcher → 静态合网格 → 大规模对象改 DOTS。池化已把生成阶段 GC 压掉。

为什么还做了一个浏览器版？

面试/投屏环境不一定装了 Unity，浏览器版零安装、离线可跑，先证明「东西能玩」；Unity 工程才是源码交付物。两份实现的配置、生成规则与碰撞逻辑一一对应，也当作同一套设计跨引擎复现的练习。
